01.6 操作系统基础与进程线程模型

所属知识域：域1 Java核心与编码工程化（计算机基础） 加工来源：javaguide/cs-basics/os-questions-01（sources/javaguide/cs-basics/os-questions-01.md） 关联文档：01.5 计算机网络 · I/O 多路复用（网络系统调用与本篇互为上下文）

模块一 · 用户态/内核态与系统调用

1. 核心原理

用户态/内核态是 CPU 特权级别，不是进程类型。进入内核态的三类事件：

事件 触发方式 同步性 典型场景
系统调用（Trap） 当前指令主动触发（syscall/ecall） 同步 read()、send()
硬件中断 外部硬件触发，与当前指令无关 异步 定时器、网卡、磁盘
同步异常 当前指令触发 同步 除零、Page Fault（可能是可恢复的懒分配/COW）

系统调用 vs 库函数：库函数（如 glibc read()）在用户态按 ABI 准备系统调用号和参数，再执行特权指令进入内核——不是一个层次的概念。

2. 生产落地

Java 视角的系统调用映射：文件 IO（FileInputStream → read 系统调用）、网络 IO（Socket → send/recv）、线程阻塞唤醒（park → futex）、内存分配（mmap/brk）。性能剖析（async-profiler/arthas）看到的系统态耗时即内核态时间。

用户态/内核态切换 ≠ 线程上下文切换：只有调度器切换到另一个执行实体才是上下文切换。系统调用很快返回时无上下文切换——这是「频繁系统调用开销大」与「线程切换开销更大」的辨析关键。

3. 踩坑规避

  • 把 Page Fault 一律当程序错误：正常场景也会触发（懒分配、COW、缺页调页），只有内核无法修复时才投递 SIGSEGV；
  • 误判 load 高 = CPU 忙：load 统计的是 R（可运行）+ D（不可中断睡眠） 任务数，D 状态高说明在等块设备/网络存储/Swap，此时 CPU 可能空闲——需结合 vmstat 的 wa/b/pidstat 一起看；
  • 连接数爆了只看应用层：先查 ulimit -n（进程 fd 上限）与内核内存。

4. 优化进阶

系统调用批量化的本质：一次系统调用的固定成本（特权切换 + 内核入口/出口 + 权限检查）远高于多带几个参数，所以有 readv/writev（聚合 IO）、io_uring（共享环形缓冲批量提交，Linux 5.1+）等批量接口——与 Redis Pipeline、MySQL 组提交是同一种思想。

5. 选型对比

机制 成本量级 适用
普通函数调用 纳秒级 用户态内部计算
系统调用 百纳秒~微秒级 必须内核服务的 IO/内存/进程操作
线程上下文切换 微秒级（同进程）/ 数十微秒（跨进程含 TLB 失效） 并发调度
进程创建 fork 毫秒级 隔离性要求高的场景（Worker 进程）

模块二 · 进程/线程模型与调度

1. 核心原理

  • 进程 = 资源分配与隔离单位（独立地址空间、文件句柄）；线程 = CPU 调度执行单位（共享堆/方法区，私有栈/PC/寄存器）；
  • PCB/TCB：Linux 不严格拆分，统一 task_struct，靠资源结构是否共享区分——地址空间/文件表是资源边界，栈/寄存器/PC 是执行现场；
  • 调度算法谱系：FCFS（护航效应）→ SJF（饥饿）→ RR（时间片权衡）→ 优先级（饥饿）→ MLFQ（按行为升降级）；Linux 主线 CFS（vruntime 公平）+ Linux 6.6+ EEVDF；
  • 同步原语：互斥锁/读写锁/信号量/屏障/条件变量——Java synchronized、ReentrantLock、Semaphore、CyclicBarrier、Condition 分别是 OS 层的封装。

2. 生产落地

  • JVM 线程数规划：-Xss（默认 1MB）决定单线程栈占用，万级线程仅栈就 GB 级——高并发用线程池 + 异步化（见 01.3 并发 · 线程池模块）；
  • CPU 密集型 vs IO 密集型：线程数 ≈ CPU 核数（前者）/ CPU 核数 × (1 + 等待/计算比)（后者）；
  • Java 死锁检测：jstack -l <pid> 或 ThreadMXBean.findDeadlockedThreads()——对应 OS 层的资源分配图环检测。

3. 踩坑规避

  • 僵尸进程：父进程不 wait() 回收已退出子进程，内核残留 PCB 占内存——Java 中表现为 Process.waitFor() 未调用；
  • 多线程一定更快？线程数远超核数后，上下文切换 + 缓存失效 + 锁竞争使吞吐延迟双降；
  • 跨进程共享状态图省事用共享内存：忘了配信号量/futex 同步就是数据竞争。

4. 优化进阶

线程模型与 GC 的联动：JVM 并行 GC 线程数、G1 并发标记线程都吃 CPU 配额；容器化环境下 -XX:ActiveProcessorCount 按 cgroup 限额设置，避免按宿主机核数超配。

上下文切换的缓存视角：同进程线程切换保留 TLB 与 L1/L2 缓存局部性，跨进程切换几乎全部失效——这就是「线程池优于进程池」的硬件层根因。

5. 选型对比

通信/并发方式 隔离性 开销 数据共享 Java 场景
多进程 + IPC 强 高 需序列化/共享内存 多 JVM 部署、Worker 隔离
多线程 弱（互相影响） 低 直接共享堆 服务内并发默认形态
协程/虚拟线程 弱 极低 直接共享堆 JDK 21 虚拟线程高 IO 并发
事件循环（epoll） 单线程顺序 最低 无竞争 Redis/Netty/Node 模型

模块三 · 内存管理：虚拟内存与分页

加工来源：小林coding《为什么要有虚拟内存？》（sources/xiaolincoding/os/virtual-memory.md）

1. 核心原理

虚拟内存：OS 为每进程分配独立虚拟地址空间，进程持虚拟地址经 MMU 映射到物理地址——解决多进程地址冲突 + 进程隔离 + 越权保护（页表项权限位）。

分段 vs 分页：

维度 分段 分页
单位 逻辑段（代码/数据/栈/堆，长度不固定） 固定 4KB 页
碎片 无内部碎片，有外部碎片 无外部碎片，有内部碎片（不足一页分一页）
内存交换 整段写盘，效率低 按页换出，效率高
地址结构 段选择子 + 段内偏移 页号 + 页内偏移

缺页异常：访问的虚拟地址页表中没有 → 内核分配物理页、更新页表、恢复运行（Page Fault 不一定是错误，也可能是可恢复的懒分配/COW，见模块一）。

多级页表：32 位 4GB 空间单级页表要 4MB/进程（100 进程 = 400MB）；二级页表靠局部性原理按需创建，20% 使用率时仅 0.804MB。64 位用四级：PGD → PUD → PMD → PTE。

TLB：CPU 内缓存最常访问页表项的 Cache，先查 TLB 未命中才查页表——用硬件换时间。

Linux 布局：主要分页，但 Intel x86 段机制不可避免——Linux 让所有段基地址为 0 覆盖整个 4GB，段只用于访问控制和内存保护；虚拟空间分内核区（32 位 1G 高地址 / 64 位 128T）与用户区；用户区从低到高：代码段 → 数据段 → BSS → 堆（向上）→ 文件映射区（向上）→ 栈（固定 8MB），低地址有保留区防 NULL 解引用跑飞。

2. 生产落地

  • JVM 堆外内存踩点：-XX:MaxDirectMemorySize 之外的 direct memory 走 mmap（文件映射段），不受堆参数控制，泄漏时 Native Memory Tracking（NMT）定位；
  • 栈容量排查：线程栈默认 8MB（ulimit -s），-Xss 调小可提升单进程线程数上限，但递归深的方法有 StackOverflowError 风险；
  • Swap 策略：vm.swappiness 生产建议 10（尽量用物理内存，避免 JVM 堆被换出导致 GC 停顿放大）；mlockall（ES 等）锁内存防换出。

3. 踩坑规避

  • 物理内存够却 OOM（killer）：容器内 Java 只看 -Xmx 不管容器 cgroup limit——堆外（元空间/线程栈/direct/glibc arena）能顶穿 cgroup，被 Linux OOM Killer 杀进程；
  • fork 的 COW 陷阱：Redis bgsave/AOF 重写 fork 时页表复制 + COW 可能使内存翻倍（见 02.2 大 Key 治理模块）；
  • 高并发下缺页抖动：JVM 大对象/新分配页频繁触发 Page Fault，表现为 CPU sys 高——提前预热 + -XX:+AlwaysPreTouch。

4. 优化进阶

三级存储的成本阶梯（磁盘比内存慢几万倍）：寄存器（1 周期）→ L1/L2/L3（ns~十 ns）→ 内存（百 ns）→ SSD（μs）→ 磁盘（ms）。虚拟内存的本质是用软件机制把这个阶梯对进程透明化，用局部性原理「假装内存无限大」。

5. 选型对比

机制 空间开销 时间开销 适用
单级页表 4MB/进程（32 位） 1 次访存 地址空间小的系统
多级页表 按需创建（~0.8MB） 4 次访存（64 位） 现代 OS 通用
多级页表 + TLB 同多级 TLB 命中 ~1 周期 生产实际形态

模块四 · 文件系统：inode 与目录项

加工来源：小林《文件系统全家桶》（https://xiaolincoding.com/os/6_file_system/file_system.html）。零拷贝见 01.5。

1. 核心原理

每个文件两套结构。inode 在磁盘上，记大小、权限、时间和数据块位置，是文件的唯一标识。目录项 dentry 在内存里，记名字和指向 inode 的关系，用来把路径拼成树。一个 inode 可以对应多个目录项，硬链接就是这样。目录本身也是文件，里面存的是子项，不是文件正文。

磁盘按 512B 扇区读写太碎，文件系统把扇区组成 4KB 逻辑块。盘上分成超级块、inode 区、数据块区。超级块在挂载时进内存，inode 在文件被访问时进内存。

2. 生产落地

用户只跟 VFS 打交道：open 拿到 fd，再 read/write/close。Ext4、XFS 是磁盘文件系统；/proc、/sys 是内存里的内核数据；NFS 是远程。应用不关心底下是哪一种。

3. 踩坑规避

  • 把目录项当成磁盘上的目录文件：dentry 是缓存，掉电不在。
  • 删掉一个硬链接就以为数据没了：还要看 inode 的链接计数。
  • 超级块损坏且没有副本：整块文件系统的结构信息会丢。

4. 优化进阶

重复解析同一路径时走 dentry 缓存，不要每次都从盘上读目录。日志文件系统把元数据变更先记日志，崩溃后按日志重放，避免超级块和 inode 对不上。具体日志格式以所用文件系统为准。

5. 选型对比

inode dentry
存放 磁盘 内存
内容 元数据和块位置 名字和父子关系
关系 一个文件一个 一个文件可有多个名字
