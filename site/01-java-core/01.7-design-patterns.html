所属知识域：域1 Java核心与编码工程化 加工来源：javaup《设计模式概述与基本原则》《单例模式深度解析》《工厂模式体系》《结构型设计模式》《行为型设计模式》《MVC与组合实战》（sources/javaup/design-pattern/） 关联文档：01.3 Java 并发编程工程化（单例与 DCL 的 volatile 语义）、02.3 Spring & MyBatis 工程化（框架中的模式应用）、07.1 实战项目案例库（Ragent 11 种设计模式实战映射）

模块一 · 设计原则：SOLID 与补充法则

1. 核心原理

七大原则总表（SOLID 五条 + 补充两条）：

原则 一句话定义 违反的典型信号
SRP 单一职责 一个类只承担一个引起变化的原因 一个类同时改需求 A 和需求 B
OCP 开闭 对扩展开放，对修改封闭 加功能就改老代码，回归风险高
LSP 里氏替换 子类能完全替代父类不出错 子类重写后抛异常/空实现
DIP 依赖倒置 高层与低层都依赖抽象，面向接口编程 业务代码直接 new 具体实现
ISP 接口隔离 客户端不依赖不需要的方法 实现类大量 throw new UnsupportedOperationException
LoD 迪米特 对象对其他对象了解最少 a.getB().getC().doSomething() 链式跨层调用
CARP 合成复用 优先组合/聚合，少用继承 继承树过深，为复用强行继承

2. 生产落地

依赖倒置的工程形态：Spring 的依赖注入即 DIP 的标准实践——Controller/Service 依赖接口，容器启动时装配具体实现；MyBatis 的 Mapper 接口 + SqlSession 模板同理（见 02.3）。

合成复用的工程形态：Ragent 项目中大量"接口 + 多实现 + 策略工厂"结构——如 LLM 客户端 AiClient 接口 + 多 Provider 实现，通过组合注入而非继承扩展（见 07.1 设计模式映射表）。

3. 踩坑规避

  • 为用模式而用模式：简单 if-else 能解决的不要上策略工厂——模式的价值在"变化被隔离"，没有变化就是过度设计；
  • 接口爆炸：ISP 走到极端给每个方法建接口——按"客户端视角"拆接口，不是按方法拆；
  • 继承滥用：CARP 的实践底线——"is-a" 才继承，"has-a" 用组合。

4. 优化进阶

原则冲突时的裁决顺序：OCP > DIP > SRP > 其余。开闭是目标，依赖倒置是手段，单一职责是拆解依据。评审中争论"要不要拆类"时，用 SRP 的"引起变化的原因"计数法裁决：数一数这个类有几个独立的修改理由。

5. 选型对比

维度 继承 组合
耦合时机 编译期静态绑定 运行期动态装配
扩展性 受父类约束 自由替换部件
适用 稳定的 is-a 关系 多变的 has-a 关系

模块二 · 单例模式深度：写法、破坏与防护

1. 核心原理

单例三要点：私有构造、静态访问点、线程安全。五种经典写法的本质差异在初始化时机与同步代价的取舍：

写法 初始化时机 线程安全机制 懒加载
饿汉式 类加载时 JVM 类初始化保证 ❌
静态内部类 首次 getInstance JVM 类初始化保证 ✅
DCL 首次 getInstance volatile + 双重检查 ✅
懒汉式（synchronized 方法） 首次 getInstance 方法级锁 ✅（每次调用都同步，性能差）
枚举 类加载时 JVM + final ❌

2. 生产落地

静态内部类（懒加载首选）：

public class CacheManager {
    private CacheManager() {}

    private static class CacheManagerHolder {
        private static final CacheManager INSTANCE = new CacheManager();
    }

    public static CacheManager getInstance() {
        return CacheManagerHolder.INSTANCE;  // 触发内部类初始化，JVM 保证同步
    }
}

DCL（需兼容老代码或需在构造中持有参数时）：

public class ServiceRegistry {
    private volatile static ServiceRegistry instance;  // volatile 不可省

    private ServiceRegistry() {}

    public static ServiceRegistry getInstance() {
        if (instance == null) {                       // ① 无锁快路径
            synchronized (ServiceRegistry.class) {
                if (instance == null) {               // ② 防重复创建
                    instance = new ServiceRegistry();
                }
            }
        }
        return instance;
    }
}

volatile 的必要性：new 的三步（分配内存 → 初始化 → 引用指向地址）可被重排，无 volatile 时另一线程可能看到"非空但未初始化"的引用（详见 01.3 模块四 JMM 的 happens-before 分析）。

枚举（最安全）：

public enum GlobalConfig {
    INSTANCE;
    private String appName = "MyApplication";
    // GlobalConfig.INSTANCE.getAppName();
}

3. 踩坑规避

两条破坏路径与防护：

攻击 机理 防护
反射 setAccessible(true) 绕过私有构造 构造函数内判空抛异常
序列化 ObjectInputStream 经 Unsafe 创建新对象 定义 private Object readResolve() { return instance; }

DCL 的 volatile 遗漏：面试与生产审查高频错误——去掉 volatile 在高并发下有 50% 概率拿到半初始化对象。

4. 优化进阶

CAS 无锁单例：AtomicReference + compareAndSet(null, instance) 自旋获取，无锁但高并发下可能创建多个临时对象（GC 压力）——仅性能极端敏感且低并发初始化时考虑。

5. 选型对比（最佳实践裁决）

  1. 首选枚举：简洁 + 天然防反射/序列化破坏（Effective Java 推荐）；
  2. 需要懒加载：静态内部类；
  3. 老代码改造/构造需参数：DCL + readResolve + 构造检查三件套；
  4. 性能敏感且初始化并发低：CAS 方案（评估自旋与临时对象开销）。

模块三 · 工厂模式三变体与选型

1. 核心原理

工厂的本质是用方法调用替代 new，把「创建哪一类、怎么初始化」从业务代码里抽走。三变体的差异在抽象层级：

变体 工厂形态 产品范围 扩展新产品 开闭原则
简单工厂 一个静态方法/类 一类产品等级 改工厂 switch ❌
工厂方法 每产品一工厂子类 一类产品等级 加产品+工厂 ✅
抽象工厂 每产品族一工厂 多等级产品族 加族工厂易；加等级难 部分

抽象工厂的「开闭倾斜」：新增 Windows/Mac 一整族组件只需新工厂；若所有族都要加 Slider，抽象接口与全部实现都得改。

2. 生产落地

简单工厂（产品少且稳定）：文档解析器按 MIME/type 字符串创建——业务侧只调 DocumentParserFactory.createParser(type)。

工厂方法（产品常变）：每种解析器对应 XxxParserFactory，新增 HTML 只加类对，不动老工厂。

抽象工厂（产品族一致性）：UIFactory 同时产出 Button/TextField/Checkbox，保证同风格组件不会混搭。

Spring 场景裁决：IoC 容器本身就是超级工厂——优先 @Component + 注入，而不是手写静态工厂；手写工厂只在「非 Spring 管理对象 / SPI 插件边界 / 明确要按字符串路由」时使用。

源码对照：Calendar.getInstance、Stream 的 Collectors、Spring BeanFactory.getBean 都是工厂思想的工程形态。

3. 踩坑规避

  • 简单工厂膨胀成上帝类：switch 超过 5~7 分支且仍在涨 → 升工厂方法或用 Spring Map 注入；
  • 为抽象工厂而抽象工厂：没有产品族（只是多个无关产品）时上抽象工厂 = 过度设计，用工厂方法即可；
  • 工厂返回具体类型：客户端依赖实现类 → 丢掉解耦收益，返回值必须是产品抽象。

4. 优化进阶

策略工厂合一：行为型策略常与工厂联用——Map<String, DeliveryStrategy> 由 Spring 按 Bean 名自动注入，工厂只做查找与缺省兜底（见模块五）。这是 Java 后端最高频的「创建型 + 行为型」组合。

5. 选型对比

  1. 类型 ≤5 且几乎不变 → 简单工厂；
  2. 单等级、类型常增 → 工厂方法；
  3. 多等级必须成套一致 → 抽象工厂；
  4. 已在 Spring 容器内 → 优先 Bean + Map 注入，少写静态工厂。

模块四 · 结构型：代理 · 享元 · 不可变

1. 核心原理

模式 一句话 解决的问题
代理 替身控制访问并可加横切逻辑 不改原类做增强
享元 共享内部状态，外部状态外传 海量相似对象的内存
不可变 创建后状态不可变 并发下的安全共享

代理场景谱系：远程（Dubbo）、动态（JDK/CGLIB → Spring AOP）、缓存/日志/权限/异常转换。

享元关键切分：内部状态可共享（树的纹理类型）、外部状态每次传入（坐标）。JDK 实证：String 池、IntegerCache（-128~127）。

不可变四规则：类 final、字段 final、无 setter、可变成员防御性拷贝。

2. 生产落地

静态缓存代理：CachedUserServiceProxy 实现同一接口，先查 ConcurrentHashMap 再委托真实服务。

AOP 通用代理：自定义 @Cacheable + @Around，比手写代理类更可扩展——与 02.3 Spring AOP 同构。

不可变值对象：交易记录、Money；「修改」一律返回新实例（withAmount / addTag）。可与享元结合缓存常用面额。

工程映射：MyBatis Plugin / Filter 链 ≈ 代理叠层；连接池/线程池 ≈ 享元式复用；java.time / String ≈ 不可变。

3. 踩坑规避

  • 包装类当锁：Long.valueOf(1) 在缓存区间是同一对象 → 两个字段同步实际互斥；锁对象用 new Object()；
  • 假不可变：final Address address 但 Address 可变且 getter 直接返回引用 → 必须入参/出参深拷贝或返回不可变视图；
  • 代理泄漏真实对象：业务拿到实现类引用绕过代理 → 接口编程 + 只注入接口类型。

4. 优化进阶

代理链过长会放大调用延迟——生产上把「必经横切」（鉴权、审计）留在网关/Filter，业务内代理只保留真正需要按方法粒度控制的增强。享元工厂注意并发下 computeIfAbsent 与缓存上限（防泄漏）。

5. 选型对比

需求 选
不改类加缓存/日志/权限 代理（优先 AOP）
十万级相似对象 享元
跨线程共享值对象 不可变（可再加享元缓存）
适配旧接口 / 包一层简化 API 适配器 / 门面（本站未专篇，思想同「包装边界」）

模块五 · 行为型：策略 · 模板 · 观察者 · 责任链 · 状态

1. 核心原理

模式 核心 与相近模式的边界
策略 算法可替换 vs 状态：策略由外部选定；状态由对象内部流转切换行为
模板方法 骨架固定、步骤可变 vs 策略：模板用继承；策略用组合（更符合 CARP）
观察者 一对多通知 Spring Event 是工程化观察者
责任链 沿链传递直至处理 Filter / Interceptor / 审批流
状态 行为随状态变 显式状态机，拒绝非法转移

2. 生产落地

策略 + 模板 + Spring Map 工厂（配送/支付同构）：

@Component
public class DeliveryStrategyFactory {
    @Autowired
    private Map<String, DeliveryStrategy> strategyMap; // Bean名 → 实例

    public DeliveryStrategy getStrategy(String type) {
        DeliveryStrategy s = strategyMap.get(type + "DeliveryStrategy");
        if (s == null) throw new IllegalArgumentException("不支持: " + type);
        return s;
    }
}

抽象策略里用模板方法固定 validate → doDeliver → notify，子类只实现 doDeliver。

观察者：价格主题注册降价推送 / 日志 / 库存预警；生产优先 Spring ApplicationEventPublisher。

责任链：退款校验→客服→主管→经理；金额阈值决定终结节点。Ragent 后处理链、12306 校验链、MyBatis Interceptor 同构（见 07.1）。

状态：工单 Draft→Open→InProgress→Resolved→Closed；非法操作在状态类内拒绝，避免巨型 if (status==X)。

3. 踩坑规避

  • 策略爆炸 + 无注册表：策略很多却用巨型 if 选策略 → 必须工厂/Map；
  • 责任链静默吞请求：链尾无兜底 → 请求「处理成功」实则未处理，链尾必须显式失败或默认处理器；
  • 状态机散落在 Service：状态转移逻辑写在业务方法各处 → 集中到状态类或专用状态机组件；
  • 观察者同步阻塞：一个慢观察者拖垮发布线程 → 异步事件或事务后提交（@TransactionalEventListener）。

4. 优化进阶

高频组合：策略 + 工厂 + 模板（支付/配送/导出）；责任链 + 状态（审批流每个节点是状态，节点内校验是链）。MVC 下 Controller 编排、Service 用策略/状态，VO 与领域分离（见 sources mvc-and-practice.md）。

5. 选型对比

场景 首选
按类型选算法（支付渠道、配送方式） 策略 + Map 工厂
流程 80% 相同、步骤差异 模板方法（或策略组合）
一事多反应（审计、通知、指标） 观察者 / Spring Event
有序校验/审批/Filter 责任链
生命周期状态驱动行为 状态模式 / 状态机
