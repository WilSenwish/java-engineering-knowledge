04.2 传统云原生工程化（Docker · K8s · 发布策略）

所属知识域：域4 工程交付与云原生 加工来源：javaup Docker 三篇 + 发布策略 + link-flow 蓝绿/灰度/滚动；xiaolincoding Docker 面试题（sources/javaup/docker/、architecture/deploy-strategy.md、link-flow/、xiaolincoding/docker/） 关联文档：04.1 AI 原生研发、05.1 线上排查、05.2 可观测性、03.2 微服务

模块一 · Docker 核心：隔离、镜像与交付

1. 核心原理

容器 = 被 Namespace 隔离视图 + 被 Cgroup 限额的特殊进程组，共享宿主机内核。镜像是 UnionFS 分层只读模板；容器在其上叠加可写层（CoW）。三大件：Image / Container / Registry。

对比 虚拟机 容器
虚拟化对象 整套 OS 进程
启动 / 密度 慢 / 低 秒级 / 高
隔离强度 强 中（共内核）

Namespace 六件套（PID/Net/Mount/UTS/IPC/User）管「看见什么」；Cgroup（含 v2 统一层次）管「能用多少」。

2. 生产落地

Java 多阶段构建（体积+安全）：

FROM maven:3.8-openjdk-17 AS builder
WORKDIR /build
COPY pom.xml . 
COPY src ./src
RUN mvn package -DskipTests

FROM openjdk:17-jdk-slim
WORKDIR /app
COPY --from=builder /build/target/*.jar app.jar
RUN useradd -m appuser
USER appuser
EXPOSE 8080
HEALTHCHECK --interval=30s --timeout=3s CMD curl -f http://localhost:8080/actuator/health || exit 1
ENTRYPOINT ["java", "-jar", "/app/app.jar"]

运行侧：--cpus / --memory / --memory-swap 防吵闹邻居；数据用 named volume；同业务容器进自定义 network，用服务名发现。

镜像规范：registry/ns/repo:tag（禁止生产依赖可变 latest）；私有仓 Harbor/ACR；国内配 registry-mirrors。

3. 踩坑规避

  • 把可变层放前面：先 COPY 源码再 npm/mvn install → 缓存全失效；应先依赖清单再源码；
  • 容器当虚机存数据：删容器丢库 → 必须 volume；
  • 包装类/root 跑生产：默认 root + 过大镜像面大 → 非 root + slim/distroless；
  • EXPOSE 当开放端口：只是声明，真正映射靠 -p / Service。

4. 优化进阶

合并 RUN 减层；.dockerignore；Alpine/distroless；构建机与运行架构一致（Apple Silicon 注意 --platform）。镜像安全扫描进 CI（Trivy 等）。

5. 选型对比

场景 选
开发联调多中间件 Compose + bind mount
单机/小流量生产 Compose + volume + restart 策略
多机高可用/自愈 上 K8s（模块二）
强租户隔离 / 异 OS VM（或 VM 上跑容器）

模块二 · 编排：Compose → Kubernetes 最小闭环

1. 核心原理

Compose 用 YAML 声明多容器应用（services/networks/volumes），适合单机。规模上来后缺跨主机调度、自愈、统一负载与声明式滚动——这是 K8s 的定位。

K8s 最小闭环：

对象 职责
Pod 最小调度单元（可 sidecar）
Deployment 副本、滚动更新、声明期望状态
Service 稳定虚拟 IP / DNS，屏蔽 Pod 漂移
Probe readiness 决定是否接流量；liveness 决定是否重启

2. 生产落地

Deployment 要点（滚动）：

spec:
  replicas: 10
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 2
      maxUnavailable: 1
  template:
    spec:
      containers:
      - name: api
        image: registry.example.com/api:v2.0
        resources:
          requests: { cpu: "500m", memory: "512Mi" }
          limits: { cpu: "1", memory: "1Gi" }
        readinessProbe:
          httpGet: { path: /actuator/health, port: 8080 }
          initialDelaySeconds: 30
          periodSeconds: 10
        livenessProbe:
          httpGet: { path: /actuator/health/liveness, port: 8080 }
          initialDelaySeconds: 60

资源：requests 保调度，limits 防打满节点；与 Docker --memory 同思想，落到调度器。

Service：selector 匹配 Pod label；蓝绿时只改 selector 的 version 即可切流（见模块三）。

3. 踩坑规避

  • 只有 liveness 没有 readiness：未就绪就接流量 → 滚动必抖；
  • limits << 实际峰值：频繁 OOMKill；要结合 05.1 看 RSS/堆；
  • Compose depends_on 当就绪：只保证启动顺序，不保证服务可用 → 用 healthcheck 或应用重试；
  • 一个 Pod 塞无关进程：违背「紧密协作才共 Pod」——网关与业务应分 Deployment。

4. 优化进阶

HPA 按 CPU/自定义指标扩缩；PDB 保滚动时最小可用；配置与密钥用 ConfigMap/Secret，镜像只含代码。可观测性接入见 05.2。

5. 选型对比

Compose K8s
学习/运维成本 低 高
自愈 / 调度 / HPA 弱 强
适用 开发、演示、小型单机 多节点生产微服务

模块三 · 发布策略与交付流水线

1. 核心原理

发布要同时满足：风险可控、体验无损、可快回滚。

策略 本质 资源 回滚
蓝绿 两套环境，切流量 约 2× 秒级（改 LB/Service）
金丝雀/灰度 小流量验证再放量 低~中 调权重归零
滚动 同集群分批换实例 低 较慢（逆向滚动）

灰度维度：机器比例、地域、VIP/白名单、userId % 100。网格层可用 Istio VirtualService weight + DestinationRule subset；业务层可用灰度路由封装。

2. 生产落地

蓝绿（K8s）：blue/green 两套 Deployment（不同 version label）→ Service selector 指向当前色 → 验证后 kubectl patch service 改 version → 异常立刻 patch 回去。

滚动：依赖 Probe + maxSurge/maxUnavailable；发布前写基线（commit、镜像 tag、配置快照）支撑一键 kubectl set image 回滚。

CI/CD 最小闭环（工程约定，工具可换）：

  1. CI：编译 → 单测 → 构建镜像 → 扫描 → 推送不可变 tag（gitsha/semver）；
  2. CD：部署到预发 → 探针/冒烟 → 按策略放量（优先金丝雀）→ 指标门禁（5xx、延迟、业务转化）；
  3. 制品：镜像仓库 +（可选）Helm/Kustomize 清单同版本；禁止「服务器上 docker build」。

GitHub Actions / GitLab CI 只是触发器；门禁与回滚策略才是交付质量核心。

3. 踩坑规避

  • 蓝绿忽略 schema：DB 变更必须扩展兼容（先加列双写，再切读，最后删旧）；
  • 灰度无指标门禁：放量靠拍脑袋 → 错误率阈值 + 自动回滚脚本；
  • 滚动当无损：窗口期内新旧共存，接口必须双向兼容；
  • latest 标签发布：无法追溯与回滚 → 不可变 tag + 基线库。

4. 优化进阶

流量染色（header x-user-type=vip）做精准金丝雀；核心链路蓝绿，一般服务金丝雀，内部工具滚动。发布与 03.3 雪崩防护 联动：放量期收紧限流/熔断阈值。

5. 选型对比

  1. 核心交易 / 强合规 → 蓝绿（预算够）；
  2. C 端体验敏感 → 金丝雀 + 真实用户指标；
  3. 内部服务 / 资源紧 → 滚动 + 强 Probe；
  4. 要对比转化 → A/B（独立实验框架，不止部署策略）。

模块四 · 指标从哪来，以及 HPA 怎么用

加工来源：Kubernetes《Metrics For Kubernetes System Components》、Horizontal Pod Autoscaling。OTel/SLO/Thanos 见 05.3。

1. 核心原理

三套数不要混：

来源 回答的问题 入口
kubelet cAdvisor 容器真正用了多少 CPU/内存，以及 PSI 停顿 kubelet /metrics/cadvisor
kubelet resource / Metrics Server 给 HPA 用的 Pod 资源用量 metrics.k8s.io
kube-state-metrics 对象「期望 vs 现状」（副本、重启次数），不是用量 监听 API，自己暴露 /metrics
控制面组件 apiserver、scheduler、controller-manager 自身 各自 /metrics，要 RBAC

HPA 是控制循环，默认约 15 秒一次。它改的是工作负载的 scale 子资源，不作用于 DaemonSet。CPU 目标按 request 的百分比 算，容器没写 request，这条指标无效，控制器不会按它扩容。

副本公式：ceil(当前副本 × 当前指标 / 目标指标)。比值落在 1.0±0.1 内不动作，避免抖动。

2. 生产落地

业务 Deployment 写 resources.requests，再挂 HPA，指标走 Metrics Server。容量规划和「有多少 Pod Pending」看 kube-state-metrics，不看 cAdvisor。节点压力看 /metrics/cadvisor 上的 PSI：some 表示有任务在等，full 表示全都停了；avg10 远高于 avg300 是刚发生的尖峰。需要 cgroup v2 和较新内核。

入口流量用 Ingress 把主机名和路径转到 Service。只允许指定命名空间互访用 NetworkPolicy，默认拒绝要显式写。有稳定网络身份和每副本一块盘的用 StatefulSet，无状态用 Deployment。Operator 是把这类对象的升级和修复写成控制器，不是又一种工作负载。

3. 踩坑规避

  • 用 limit 或宿主机 top 对 HPA：HPA 看的是相对 request 的用量。
  • 没装 Metrics Server 就配 HPA：metrics.k8s.io 空的，副本不动。
  • 把 kube-state-metrics 的副本数当成 CPU：它不采集用量。
  • 控制面指标升级后消失：稳定指标废弃后会先隐藏。临时打开用 --show-hidden-metrics-for-version，且只能指向上一个小版本。

4. 优化进阶

自定义或外部指标走 custom.metrics.k8s.io / external.metrics.k8s.io（队列长度、QPS），和 CPU 目标可以同时存在，取算出的最大副本。基数用 --allow-metric-labels 限制，避免无界标签打满组件内存。

5. 选型对比

需求 用
按 CPU/内存加减 Pod HPA + requests
给单个 Pod 加内存 VPA（另一条回路，不在 HPA 里）
每个节点一个 DaemonSet，不能 HPA
看对象是否就绪 kube-state-metrics
看容器是否在等 CPU/IO cAdvisor PSI
