## 模块一 · OpenTelemetry：信号怎么串起来

### 1. 核心原理

OTel 采集并导出信号：Trace（一次请求穿过哪些组件）、Metric（某个时刻的测量）、Log（事件记录）、Baggage（在信号之间传递的上下文）。它们靠 **trace context** 对齐：span 用 parent/links，指标用 exemplar 带上 trace id，日志把同一 context 写进记录。没有传递，三支柱只是三套互不认识的数据。

### 2. 生产落地

Java 先上 **Java agent**（启动时改字节码，按依赖自动埋点），Spring 应用可用 starter。入口从入站消息 extract context，出口 inject 到出站 HTTP/MQ。日志继续用 SLF4J/Logback，用 appender 桥进 OTel，或打到 stdout 再由采集器转发；OTel 的 Logger API 是桥，不是业务日志门面。

语义约定规定 span 名、指标单位和属性键，跨服务才能对上同一字段。

### 3. 踩坑规避

- 只开 trace、日志不带 trace id：排障时对不上。
- 本地和测试没装 agent，手写埋点又假定 `GlobalOpenTelemetry` 一定存在：要能退到空实现。
- 把全部日志改成直连 Collector：应用要自己排队和重试；吞吐敏感时仍走文件/stdout。

### 4. 优化进阶

已有 Micrometer / SkyWalking 时用官方 shim 桥接，不要两套 SDK 各打一份相同指标。Collector 放在进程外做采样、改名和路由，应用只负责产生信号。

### 5. 选型对比

| | Java agent | 手写 span | SkyWalking agent（见 05.2） |
|--|------------|-----------|------------------------------|
| 接入 | `-javaagent` | 业务代码 | 同样是 agent |
| 标准 | OTel 语义约定、OTLP | 取决于你写什么 | SkyWalking 协议，可再导出 |
| 适用 | 新系统、要换后端 | 领域跨度（下单号、租户） | 已在 SkyWalking 上的存量 |

## 模块二 · SLO 与错误预算

### 1. 核心原理

来自 Google SRE，三个词不要混：

| | 是什么 | 没有它会怎样 |
|--|--------|----------------|
| SLI | 用户在乎的量化指标：成功率、延迟分位 | 看了一堆机器指标仍不知道用户是否受苦 |
| SLO | SLI 的目标，例如 99% 的 Get 在 100ms 内 | 用户和值班各有一套「应该多快」 |
| SLA | 带后果的合同（赔偿、违约） | 没后果的就是 SLO |

可用性常用「成功请求 / 合法请求」，不是机器开机时间。100% 既做不到，也不该当目标：服务太稳会让别人把你当成不会挂（Chubby 的教训是故意把可用性压回目标，逼出隐藏依赖）。

**错误预算** = 允许达不到 SLO 的那一段比例。99.9% 的月目标大约留下 0.1% 的失败额度。预算还在，可以发版；预算烧完，先还可靠性。

### 2. 生产落地

面向用户的服务看可用性、延迟、吞吐；存储再加持久性；管道看端到端延迟和吞吐。指标尽量少，服务端采不到的用户体验要在客户端补（页面变可用的时间，不是只看后端 RT）。

SLO 写清测量窗口和条件：「1 分钟平均、全部后端上，99% 的 Get 小于 100ms」。交互用户和批处理用户拆开，不要一个数字打两拨人。

预算按天或周看消耗，按月向管理层汇报。发版节奏跟剩余预算挂钩，而不是跟「这周想不想上」。

### 3. 踩坑规避

- 把当前水位直接写成 SLO：以后每次优化都会被旧数字绑架。
- 追求「永远可用、延迟不随流量涨」：设计和机器都会贵到没有用户需要的程度。
- 用平均值当唯一 SLI：长尾被平均掉。SRE 原文允许多层目标（90% / 99% / 99.9% 各一个阈值）。
- 把内部 SLA 罚款和工程 SLO 当成同一份文档。

### 4. 优化进阶

告警打在「预算燃烧速度」上，而不是每一个 5xx。慢速燃烧留给工单，快速燃烧（一小时烧掉一天预算）才叫醒人。与 [04.2](../04-delivery-cloudnative/04.2-cloud-native.md) 的发布门禁对齐：错误率越过预算阈值就停止放量。

### 5. 选型对比

| 说法 | 实际 |
|------|------|
| 我们要五个九 | 先写清 SLI 是请求成功率还是进程存活 |
| 监控大盘很全 | 用户 SLI 可能一个都没有 |
| 这月没故障所以很稳 | 可能只是没有流量打到缺陷上；预算应用来允许有计划的变更 |

## 模块三 · Thanos：Prometheus 跨集群与长期保存

### 1. 核心原理

Prometheus 本地 TSDB 按时间切成不可变 block（ULID 目录，内有 chunks、index、`meta.json`）。Thanos 不改这套格式，只把 block 放到对象存储，并用同一套 **Store gRPC API** 让查询方分不清数据来自活着的 Prometheus 还是历史桶。

### 2. 生产落地

- **Sidecar**：跟每个 Prometheus 一起跑，把新 block 上传；`meta.json` 写入 external labels（集群、环境），查询时先按标签丢掉无关块。
- **Store**：盯着桶，用时间范围和标签过滤，缓存 index，chunk 按需读。chunk 太大，不进缓存。
- **Querier**：无状态，横向加实例，在 Store API 上执行 PromQL。
- **Compactor**：单独进程，合并小块、降采样、执行保留期。不要跑多份去压同一个桶。
- **Rule**：告警和记录规则离开单机 Prometheus，对着全局查询评估。

本地盘保留从数周缩到数小时，长期曲线放对象存储。

### 3. 踩坑规避

- Compactor 开成多副本同时压一个桶：块会被写乱。
- 不打 external labels：多集群序列在 Querier 里叠成一条。
- 用 Thanos 解决「指标基数爆炸」：它解决的是留存和全局查询，高基数仍会打满 Prometheus 内存。
- 把所有历史查询都打到未降采样的原始块：Store 对对象存储的请求次数跟着查询习惯涨。

### 4. 优化进阶

按地域分桶，等于给 Store 做功能分片。冷数据降采样后再给大盘。Querier 是唯一明确可以随意加的无状态层。

### 5. 选型对比

| | 单机 Prometheus | Thanos | 远程写到别的库 |
|--|-----------------|--------|----------------|
| 查询语言 | PromQL | 仍是 PromQL | 看目标系统 |
| 留存 | 本地盘 | 对象存储 | 目标库 |
| 多集群 | 各自看 | external labels + Querier | 取决于写入标签 |
| 运维 | 低 | Sidecar/Store/Compactor 要分开管 | 少一个查询层，多一种数据模型 |
